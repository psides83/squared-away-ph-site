# Receipt-assisted inventory purchases

## Available now

- Take photo or choose a file when recording a stock purchase, or when attaching a receipt to an existing expense. The camera button requests the outward-facing camera through the mobile browser’s file chooser. Actual availability depends on the device/browser; the file chooser remains available.
- Larger image files are reduced on the device before upload, retaining a maximum 2,400-pixel longest edge. Supported receipt uploads remain JPEG, PNG, WebP, and PDF, at most 3 MB. PDF files are not recompressed. Photos that cannot be decoded or reduced must be supplied as a smaller supported file.
- A purchase saves its stock movement and expense together, then attaches the private receipt. If attachment fails, the saved expense is opened for retry; do not enter the purchase again. The same receipt content attached to the same expense is deduplicated by content hash.
- Inventory → Record purchase / stock → Record a receipt now supports a manually reviewed receipt with 1–20 inventory and expense-only items, one expense, and one optional private receipt attachment. Select products/units/quantities and enter full item subtotals. One chosen expense category applies to the entire receipt; per-item category reporting is not yet implemented.
- Choose which items receive discount/tax suggestions. Discounts are proportional to eligible subtotals, then tax is proportional to eligible after-discount values. Largest-remainder cent allocation breaks ties in item order; tax eligibility and rates are never inferred. Suggestions are editable and replace the previous allocations only when requested. Review every line and printed total; changes clear the review checkbox. Allocations must exactly reconcile before saving.
- Product stock values include the reviewed allocated costs; expense-only lines add no inventory. One transaction saves all stock movements, item/conversion/product-name snapshots and the single expense. The payment date is explicit; unpaid receipts are not cash spent. Supplier-credit application remains a separate deliberate operation on the saved purchase expense.
- Expense → Receipt items shows saved lines and deliberate cancellation of an untouched whole receipt. Cancellation restores original stock and voids the expense together, retaining items/documentation/reason. Any later activity on a receipt product blocks cancellation; active supplier credit, billing/cost protections can also block it. Correct those links explicitly before retrying. Single-item source correction tools cannot overwrite multi-item receipts. Later item corrections and per-item category allocation remain future work.
- Exact request retries reuse the saved receipt without changing later payment status or restoring cancelled stock. Fresh forms now check known identical prepared-file fingerprints as described below; visual/similar receipt detection remains planned. Receipt-file validation occurs before the purchase save; upload failure after saving opens a saved-record link for attachment retry instead of re-entering stock. Requires application migration `20261028007000_multi_item_purchases.sql`.
- Free OCR.space photo-reading code is implemented below, but needs an owner-supplied free API key and production setup. No receipt has been sent to a provider during implementation.

## Free photo reading (code implemented; setup required)

The purchase form offers **Read receipt** after selecting a photo. The destination is explicitly named as OCR.space; choosing a file alone never sends it there. A completed read shows possible vendor/date/total/item values and the recognized text. **Use suggestions in draft** opens an app confirmation before replacing unsaved draft fields. Results collapse after application and remain available for comparison. You still choose item type, quantity, unit, tax eligibility and the receipt's expense category, reconcile adjustments and explicitly review/save the purchase. Payment status is never read from the receipt; applying suggestions clears its paid date.

This uses only the fixed HTTPS free OCR.space endpoint with Engine 2; it has no paid model, paid fallback, subscription creation or automatic provider retry. The provider currently documents a free API, commercial use, a 1-MB free file limit and external quotas. These are provider policies, not an app guarantee of uptime. See [free API documentation](https://ocr.space/ocrapi), [commercial-use FAQ](https://ocr.space/faq) and [provider privacy policy](https://ocr.space/privacypolicy).

### Setup

1. Apply all application migrations through `20261028007100_free_receipt_ocr.sql`, then deploy. Existing manual receipt purchases remain supported.
2. The project owner obtains a **free** OCR.space API key through the provider's registration page. Do not subscribe to a paid plan or use the public `helloworld` demo key. No account, registration, agreement or provider request was created by implementation.
3. Add `OCR_SPACE_API_KEY` as a server-only Vercel **Production** variable and set `OCR_SPACE_FREE_ENABLED=1`. The existing Supabase server secret/service-role key and project URL must also be configured for recording the private read result. Never use a `NEXT_PUBLIC_` variable for the OCR key or paste keys into chat. Redeploy after configuration. Preview/non-production and missing configuration leave reading unavailable while manual entry stays usable.
4. On the actual installed phone/browser, choose a readable sample receipt photo, review the named destination/privacy information, then deliberately tap Read receipt. Verify the original text and suggested draft against the image, complete the missing fields and review before saving. Verify the saved purchase's source in Expense → Receipt items. Actual provider accuracy, live database/storage and camera behavior remain unverified; local checks used mocked provider responses and synthetic receipt text only.

### Limits and data handling

- Purchase-form photos are re-encoded locally as JPEG to remove original image metadata and fit under 900,000 bytes, with the existing 2,400-pixel maximum edge. This also changes the photo eventually attached to the expense. A photo that cannot fit fails before reading; crop it or use a smaller supported image. PDFs up to the existing 3-MB attachment limit remain manual-entry documents; this first reader does not send PDFs.
- Every provider send requires an administrator click. App-wide caps are **20 new reads per Central Time day** and **200 per Central Time month**, with **one new read per minute per administrator**. Failed/abandoned reservations count, so network failures cannot silently exhaust quota through automatic retries. Exact repeated request IDs for the same photo return retained completed results, or pending/failed status, without sending again. Stale pending requests expire after two minutes. External provider/shared-IP limits can still reject a request earlier. Manual entry remains available.
- The server verifies image type/size before reserving or sending, uses a fixed provider destination and an API key header, rejects redirects, sets a 20-second request deadline and bounds the response to 256,000 bytes. Partial, malformed, multi-page, empty or overlong results are rejected rather than imported. Extracted text is limited to 40,000 characters. Provider error bodies and API keys are not returned to the browser or stored in read metadata.
- Private read records retain the image SHA-256, owner, provider/engine, parser version, status and recognized text for audit. The photo itself is not uploaded to Supabase merely by reading; it remains selected locally until a purchase save attaches it through the existing private receipt workflow. Recognized text/read metadata persist even if the purchase is never saved; no automatic purge of those audit records is implemented. Customers/anonymous users cannot read them, and only the originating administrator can inspect their recognized text. Completion writes are service-only; customers/admin clients cannot fabricate completed results directly.
- A purchase applied from a read must retain its matching selected photo. The server hashes the actual attached bytes, and the database checks an owned completed read before retaining the source link. A changed/removed photo clears the current read link in the form. Existing transaction/retry/cancellation guards still apply; a successful read never creates stock, expenses, payments or tax decisions itself. If receipt attachment fails after saving the purchase, retry attachment from the saved expense rather than entering it again.

### What the free reader does and does not infer

This is conservative text parsing, not an accounting model. It recognizes straightforward printed amount labels and description-plus-subtotal rows. A single valid four-digit US/ISO date may be suggested; missing/conflicting dates or amounts remain blank with review messages, including tax/discount zeros that you must confirm yourself. Item rows over the existing 20-item limit are not partly imported. Negative/unsupported rows, unusual layouts, multiple price columns and OCR errors require manual review using the full recognized text.

Only one exact normalized product-name match is suggested; ambiguous names, abbreviations and vendor-specific descriptions remain unmatched. Package weights, quantities, unit conversions, taxability and payment status are not guessed. An unmatched candidate has no item type selected; choose Inventory or Expense only explicitly. A unique exact product-name match can suggest Inventory, but its units and quantity still remain blank. Reviewed vendor aliases, layout-aware extraction, similarity-based photo/vendor/date/amount duplicate warnings, per-line category reporting, historical item corrections and a searchable read-history/recovery workspace remain planned.


## Exact-file duplicate purchase review

Migration `20261028007200_receipt_duplicate_review.sql` adds duplicate review when saving a new multi-item receipt with an attachment. This works without enabling OCR and makes no provider request. The server hashes the actual prepared file, and the database checks known hashes from saved receipt purchases plus existing content-addressed expense attachments. Earlier OCR purchase hashes are retained/backfilled; matching attachments of different types for one expense produce only one match. Voided/cancelled expenses are excluded. Files with no known hash, missing attachments and manual entries without a file cannot be compared.

If a file matches, the purchase is not created. Review existing expense links (they open separately to preserve your draft), then either use the existing record/attach its missing receipt or deliberately confirm that another purchase is intended. A private explanation is required alongside the acknowledgement and final purchase review. Matches are paged ten at a time; all matches are available and included in the saved decision snapshot. Draft edits clear approval; changing/removing the file clears its acknowledgement/explanation. A stale match set is checked again rather than accepted using the earlier token.

New receipt operations sharing a fingerprint serialize in the database, and duplicate checks run before stock/expense creation. Exact committed request retries still compare their retained payload, but do not require a new duplicate decision or recreate cancelled stock. A new purchase fingerprint is retained even if its optional receipt upload later fails. Old pre-fingerprint request retries preserve their original payload shape. An intentional separate purchase retains the matching-record snapshot, reason, actor and timestamp; Receipt items shows that history collapsed, with the originally reviewed names/dates/amounts rather than rewritten current values. Private helpers and history writes cannot bypass administrator/source guards.

This is a useful warning, not proof that two purchases are the same. It compares **identical prepared file bytes**, not receipt appearance or financial similarity. Browser preparation/re-encoding, new photos, crops and different formats can change the fingerprint. Metadata/files added later are only available to later checks, not retroactively to a previous decision. Similar vendor/date/total review and visual/perceptual matching remain planned. No actual files or financial records were changed during local verification. A 390-pixel synthetic preview checks warning/links, deliberate acknowledgement, reason spacing and match pagination. Migration application, authenticated live saves/storage and physical-device fingerprint behavior remain unverified.
